About the data

These are NYC Taxi and Limousine Commission yellow taxi trip records for January 2024, with a location lookup and the game's teaching changes. row_id and loaded_at describe the load, not the trip. Location 264 means Unknown (zone N/A); 265 means Outside of NYC.

trips_raw
  • row_id: Unique identifier for a physical row in the feed; load metadata, not a trip key.
  • vendor_id: Provider that recorded the trip.
  • pickup_at: Pick-up date and time in local time, without a time zone.
  • dropoff_at: Drop-off date and time in local time, without a time zone.
  • passenger_count: Reported number of passengers.
  • trip_distance: Reported trip distance in miles.
  • pu_location_id: Pick-up location id, matched to zones.location_id.
  • do_location_id: Drop-off location id, matched to zones.location_id.
  • payment_type: Code for the reported payment method.
  • fare_amount: Metered fare amount in dollars.
  • tip_amount: Recorded tip amount in dollars.
  • total_amount: Reported total trip amount in dollars.
  • loaded_at: When the physical row was loaded; load metadata, not a trip key.
zones
  • location_id: Location id used to match a trip location.
  • borough: Borough reported for the location.
  • zone: Name of the location.
  • service_zone: Service area reported for the location.

Source: NYC TLC trip records and Yellow taxi data dictionary (PDF). The game renames columns, for example tpep_pickup_datetime becomes pickup_at, and adds row_id and loaded_at. Use the game's column list above when writing your SQL.

Floor 1: The double shift

Cleared

The feed came in twice

The depot dashboard is overstating revenue because one delivery arrived twice. trips_raw holds every physical row in the incoming feed, including both copies, and zones names the locations. Keep one whole row per trip so the morning report counts each ride once.

SQL refresher

Read, count and save a result

SELECT chooses columns and FROM names a table. COUNT(*) counts rows. CREATE OR REPLACE TABLE ... AS saves a query result; rerunning it replaces the previous saved table.

CREATE OR REPLACE TABLE tiny AS
SELECT * FROM (VALUES (1, 12), (2, 18)) AS rides(id, fare);
SELECT count(*) FROM tiny;
A key, grain and repeated groups

Grain means what one row represents. A key is the set of columns that identifies one item at that grain. GROUP BY collects rows with the same key; HAVING filters the groups after counting. DISTINCT compares only the columns you select.

WITH deliveries(ride, fare) AS (VALUES (1, 12), (1, 12), (2, 18))
SELECT ride, fare, count(*) FROM deliveries
GROUP BY ride, fare HAVING count(*) > 1;
Keep a whole row from each group

ROW_NUMBER numbers rows inside each PARTITION BY group. ORDER BY chooses which copy comes first. QUALIFY filters the window result, so keeping number 1 preserves a whole row instead of adding its amounts.

WITH deliveries(ride, copy) AS (VALUES (1, 1), (1, 2), (2, 1))
SELECT * FROM deliveries
QUALIFY row_number() OVER (PARTITION BY ride ORDER BY copy) = 1;

The load for trips picked up on 15 January ran twice. Every trip from that day is in the table two times. So revenue looks higher than it was.

Your task: Create trips_clean with exactly one row per trip key, and every column of trips_raw. A trip key is the set of columns that together identify one trip. Two trips that differ in any amount are different trips. row_id and loaded_at describe the load, not the trip. Use CREATE OR REPLACE TABLE to run your SQL again without a DROP.

Lv 2 · How the check works

You get two tables: trips_raw (7,345 rows) and zones (265 rows). trips_clean must keep every column of trips_raw, add no columns, and change no values.

Lv 3 · The real SQL

SELECT count(*) FROM trips_raw;

SELECT loaded_at, count(*) AS rows
FROM trips_raw
GROUP BY loaded_at
ORDER BY loaded_at;

Why DISTINCT finds nothing

SELECT DISTINCT removes rows that are equal in every column. The second copies are not equal: each one has a new row_id and a later loaded_at. So DISTINCT removes nothing.

Lv 2 · How the check works

A row can be a copy even when some columns differ. Columns added by the load, like row_id and loaded_at, say how the row arrived. They do not say which trip it is.

Lv 3 · The real SQL

SELECT count(*)
FROM (SELECT DISTINCT * FROM trips_raw);  -- still 7,345

Choose a trip key

A duplicate is defined by a key you choose: the columns that together name one trip. Two rows with the same key are the same trip.

Lv 2 · How the check works

In this game the trip key is vendor_id, pickup_at, dropoff_at, pu_location_id, do_location_id and total_amount. In the full January file, this key has no duplicates.

The check: count the rows, then count the distinct keys. If the two counts differ, the table has copies.

Lv 3 · The real SQL

SELECT count(*) AS rows FROM trips_raw;

SELECT count(*) AS trips
FROM (SELECT DISTINCT vendor_id, pickup_at, dropoff_at,
                      pu_location_id, do_location_id, total_amount
      FROM trips_raw);

Keep one row per key

Number the rows inside each key, and keep row number 1. Which copy survives does not matter, as long as each trip appears once.

Lv 2 · How the check works

Do not keep only the keys that occur once: that drops both copies. Do not add up the copies with GROUP BY: the revenue stays doubled, and columns go missing.

Lv 3 · The real SQL

CREATE OR REPLACE TABLE trips_clean AS
SELECT * FROM trips_raw
QUALIFY row_number() OVER (
  PARTITION BY /* your trip key */
  ORDER BY row_id) = 1;

Count before and after

Say the count before and after, and explain the difference. Before: 7,345 rows. After: 7,171 rows. The difference, 174, is the rerun.

Lv 2 · How the check works

The check passes when trips_clean has the columns of trips_raw and no others, every row is an unchanged row of trips_raw, and it has 7,171 rows and 7,171 distinct trip keys.

Revenue (sum(total_amount)): 197,977.97 before, 193,403.10 after.

Lv 3 · The real SQL

SELECT count(*) AS rows,
       round(sum(total_amount), 2) AS revenue
FROM trips_clean;

Floor 2: Nowhere zones

Cleared

Trips to nowhere

The depot needs to report where every trip started and ended, including trips whose locations cannot be matched. trips holds 7,171 trips with rerun copies already removed; zones is the location lookup. Keeping unmatched trips in the report prevents an incomplete picture of service and revenue.

SQL refresher

Keep unmatched rows with LEFT JOIN

A JOIN matches keys between tables. A LEFT JOIN keeps every row on the left and puts NULL in the right columns when there is no match. Aliases such as r and z name the two table copies. Joining twice lets you look up two locations.

WITH rides(id, place) AS (VALUES (1, 10), (2, 99)),
places(id, name) AS (VALUES (10, 'Depot'))
SELECT r.id, z.name FROM rides r
LEFT JOIN places z ON z.id = r.place;
Label the first matching condition

CASE checks WHEN conditions in order and returns the first matching THEN value. ELSE handles the rest. Test missing values with IS NULL, not = NULL. OR means either condition can be true; IN checks membership in a list.

WITH places(id) AS (VALUES (10), (99), (NULL))
SELECT id, CASE WHEN id IS NULL THEN 'missing'
WHEN id IN (99) THEN 'outside' ELSE 'known' END AS flag
FROM places;
Save and count the joined result

CREATE OR REPLACE TABLE ... AS saves the query so you can rebuild it. COUNT(*) checks that a join kept the expected number of rows. GROUP BY makes one group per label; HAVING can filter those groups.

CREATE OR REPLACE TABLE tiny AS
SELECT * FROM (VALUES ('known'), ('missing')) AS labels(flag);
SELECT flag, count(*) FROM tiny GROUP BY flag
HAVING count(*) > 0;

Some trips start or end in a zone that is not a real place on the map. If you join to the zone lookup the wrong way, those trips vanish without an error.

Your task: create trips_clean with every row of trips, plus three columns: pu_zone, do_zone and zone_flag. Use CREATE OR REPLACE TABLE to run your SQL again without a DROP.

Checks compare values, so equivalent numbers and timestamps saved as text still count as unchanged. Money is rounded to cents; an exact half cent rounds away from zero. Every other number and timestamp keeps its full precision.

Lv 2 · How the check works

You get trips (rerun copies already removed, 7,171 rows) and zones (265 rows). pu_zone and do_zone are the zone names from zones, or NULL when there is no match.

Lv 3 · The real SQL

SELECT * FROM zones WHERE location_id IN (264, 265);

Three kinds of nowhere

  • Zone 264 is "Unknown". The lookup has it, but it names no place.
  • Zone 265 is "Outside of NYC". It is a real place, outside the zone map.
  • Some drop-off ids are 0 or NULL. They match nothing in the lookup.

Lv 2 · How the check works

110 trips touch zone 264, and 74 touch zone 265. These are real TLC rows. 25 trips have a drop-off id that matches nothing: 15 are 0 and 10 are NULL. These are planted for the game.

Lv 3 · The real SQL

SELECT do_location_id, count(*) AS trips
FROM trips
WHERE do_location_id IS NULL
   OR do_location_id NOT IN (SELECT location_id FROM zones)
GROUP BY do_location_id;

A join can drop rows

An inner join keeps only rows that match on both sides. The trips with no matching drop-off zone disappear, and nothing warns you.

Lv 2 · How the check works

With an inner join on both ids, 7,171 trips become 7,146. A LEFT JOIN keeps every trip and puts NULL where there is no match.

An anti-join (a LEFT JOIN where the lookup side IS NULL) lists the rows that match nothing. It cannot find zone 264, because 264 is in the lookup.

Lv 3 · The real SQL

SELECT count(*) FROM trips t
JOIN zones pz ON pz.location_id = t.pu_location_id
JOIN zones dz ON dz.location_id = t.do_location_id;  -- 7,146

SELECT t.row_id, t.do_location_id
FROM trips t
LEFT JOIN zones dz ON dz.location_id = t.do_location_id
WHERE dz.location_id IS NULL;  -- the 25 that match nothing

Flag, do not delete

Keep every row, and add a flag that says what is wrong. Someone later can choose what to do with it. A deleted row cannot be explained later.

Lv 2 · How the check works

zone_flag takes the first rule that applies, in this order:

  1. 'unmatched': either id is NULL or not in zones;
  2. 'unknown': either id is 264;
  3. 'outside_nyc': either id is 265;
  4. 'ok'.

The order matters: test 'unmatched' first.

Lv 3 · The real SQL

CASE WHEN /* a pickup or drop-off with no match */ THEN 'unmatched'
     WHEN t.pu_location_id = 264 OR t.do_location_id = 264 THEN 'unknown'
     WHEN /* ... 265 ... */ THEN 'outside_nyc'
     ELSE 'ok' END AS zone_flag

Count before and after

7,171 rows in, 7,171 rows out. No row is lost, and each one carries a flag.

Lv 2 · How the check works

Flags: ok 6,962, unknown 110, outside_nyc 74, unmatched 25. Together they make 7,171.

The check passes when trips_clean has 7,171 rows, keeps every column of trips unchanged, and has the expected (row_id, pu_zone, do_zone, zone_flag) values.

Lv 3 · The real SQL

SELECT zone_flag, count(*) AS trips
FROM trips_clean
GROUP BY zone_flag
ORDER BY trips DESC;

Floor 3: Impossible rides

Cleared

Impossible rides

The depot must explain rides with impossible measurements before using them in a report. trips holds 7,171 trips with zone names and zone_flag; zones is the location lookup. Separating questionable rows with a reason preserves the evidence and leaves a clean report that reconciles to the input.

SQL refresher

Filter ranges and combine conditions

WHERE keeps rows whose condition is true. Compare values with <, >= and =; use AND when both conditions must hold and OR when either may hold. A timestamp range with an inclusive start and exclusive end includes the whole final day.

WITH rides(started_at, fare) AS (VALUES (TIMESTAMP '2024-03-01', -2))
SELECT * FROM rides WHERE fare < 0
OR (started_at >= TIMESTAMP '2024-03-01' AND started_at < TIMESTAMP '2024-04-01');
Choose the first reason

CASE evaluates WHEN conditions from top to bottom. Only the first matching reason is returned, even when several rules fail. A CASE without ELSE returns NULL if no condition matches; IS NULL tests that result.

WITH rides(fare, miles) AS (VALUES (-2, 0), (10, 2))
SELECT *, CASE WHEN fare < 0 THEN 'negative'
WHEN miles = 0 THEN 'no_distance' END AS reason
FROM rides;
Save a partition without deleting evidence

CREATE OR REPLACE TABLE ... AS saves a query. Put failing rows in one table and the others in another. A subquery with NOT IN can keep ids absent from a non-NULL id list. COUNT(*) checks that the two tables reconcile; GROUP BY and HAVING can reveal repeated ids.

WITH checked(id, reason) AS (VALUES (1, 'negative'), (2, NULL))
SELECT * FROM checked WHERE id NOT IN
(SELECT id FROM checked WHERE reason IS NOT NULL);
Check counts by reason

COUNT(*) counts every row in each group. GROUP BY reason separates the labels; HAVING filters groups after counting. The clean count plus the quarantined count must equal the input count.

WITH checked(reason) AS (VALUES ('negative'), ('negative'), (NULL))
SELECT reason, count(*) FROM checked
GROUP BY reason HAVING count(*) > 0;

Lv 2 · How the check works

You get trips (zone labels already added, 7,171 rows, with zone_flag) and zones. quarantine has every column of trips plus reason. trips_clean has the columns of trips.

Lv 3 · The real SQL

SELECT min(pickup_at), max(pickup_at), min(fare_amount)
FROM trips;

Four range rules

Write one rule per problem. Count each rule on its own before you combine them.

Lv 2 · How the check works

The rules, in this order:

  1. negative_fare: fare_amount < 0
  2. time_travel: dropoff_at < pickup_at
  3. outside_january: the pick-up is before 1 January 2024, or on or after 1 February 2024
  4. zero_distance_high_fare: trip_distance = 0 and fare_amount >= 50

These four columns have no NULLs. zone_flag is not a quarantine reason.

Lv 3 · The real SQL

SELECT
  count(*) FILTER (WHERE fare_amount < 0) AS negative_fare,
  count(*) FILTER (WHERE dropoff_at < pickup_at) AS time_travel,
  count(*) FILTER (WHERE pickup_at < TIMESTAMP '2024-01-01'
                      OR pickup_at >= TIMESTAMP '2024-02-01') AS outside_january,
  count(*) FILTER (WHERE trip_distance = 0
                     AND fare_amount >= 50) AS zero_distance_high_fare
FROM trips;

The first rule wins

One row fails two rules. It goes to quarantine once, with the first reason it fails.

Lv 2 · How the check works

If you stack the four rules with UNION ALL and do not exclude earlier rules, that row appears twice: 217 rows instead of 216. A CASE tests the rules in order and stops at the first match.

Watch the January bound: pickup_at <= '2024-01-31' loses every trip on 31 January after midnight.

Lv 3 · The real SQL

CASE WHEN fare_amount < 0 THEN 'negative_fare'
     WHEN dropoff_at < pickup_at THEN 'time_travel'
     WHEN /* outside January */ THEN 'outside_january'
     WHEN /* zero miles, fare of 50 or more */ THEN 'zero_distance_high_fare'
END AS reason  -- NULL: the row passes every rule

Quarantine, do not delete

Do not delete what you cannot explain. A quarantine table keeps the failing rows and the reason, so someone can check them later.

Lv 2 · How the check works

A DELETE leaves no record of what was removed or why. With a quarantine table, every row is in exactly one place: trips_clean or quarantine.

Lv 3 · The real SQL

CREATE OR REPLACE TABLE quarantine AS
SELECT *, /* your CASE */ AS reason
FROM trips
WHERE /* the row fails a rule */;

CREATE OR REPLACE TABLE trips_clean AS
SELECT * FROM trips
WHERE row_id NOT IN (SELECT row_id FROM quarantine);

Clean plus quarantine equals raw

6,955 clean rows plus 216 quarantined rows make 7,171. If your two counts do not add up to the count you started with, a row is lost or counted twice.

Lv 2 · How the check works

By reason: negative_fare 132, zero_distance_high_fare 47, time_travel 20, outside_january 17.

The check passes when the two tables share no row_id, together hold all 7,171 row_id values of trips, and quarantine has the expected (row_id, reason) pairs.

Lv 3 · The real SQL

SELECT (SELECT count(*) FROM trips_clean) AS clean,
       (SELECT count(*) FROM quarantine)  AS quarantined,
       (SELECT count(*) FROM trips)       AS raw;
