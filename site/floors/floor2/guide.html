Trips to nowhere

{{context}} {{refresher}}

Some trips start or end in a zone that is not a real place on the map. If you join to the zone lookup the wrong way, those trips vanish without an error.

{{task}}

Lv 2 · How the check works

The check compares values, not formatting: 1.10 and 1.1 are the same, and money is compared to the cent.

You get trips (rerun copies already removed, 7,171 rows) and zones (265 rows). pu_zone and do_zone are the zone names from zones, or NULL when there is no match.

Lv 3 · The real SQL

SELECT * FROM zones WHERE location_id IN (264, 265);

Three kinds of nowhere

  • Zone 264 is "Unknown". The lookup has it, but it names no place.
  • Zone 265 is "Outside of NYC". It is a real place, outside the zone map.
  • Some drop-off ids are 0 or NULL. They match nothing in the lookup.

Lv 2 · How the check works

110 trips touch zone 264, and 74 touch zone 265. These are real TLC rows. 25 trips have a drop-off id that matches nothing: 15 are 0 and 10 are NULL. These are planted for the game.

Lv 3 · The real SQL

SELECT do_location_id, count(*) AS trips
FROM trips
WHERE do_location_id IS NULL
   OR do_location_id NOT IN (SELECT location_id FROM zones)
GROUP BY do_location_id;

A join can drop rows

An inner join keeps only rows that match on both sides. The trips with no matching drop-off zone disappear, and nothing warns you.

Lv 2 · How the check works

With an inner join on both ids, 7,171 trips become 7,146. A LEFT JOIN keeps every trip and puts NULL where there is no match.

An anti-join (a LEFT JOIN where the lookup side IS NULL) lists the rows that match nothing. It cannot find zone 264, because 264 is in the lookup.

Lv 3 · The real SQL

SELECT count(*) FROM trips t
JOIN zones pz ON pz.location_id = t.pu_location_id
JOIN zones dz ON dz.location_id = t.do_location_id;  -- 7,146

SELECT t.row_id, t.do_location_id
FROM trips t
LEFT JOIN zones dz ON dz.location_id = t.do_location_id
WHERE dz.location_id IS NULL;  -- the 25 that match nothing

Flag, do not delete

Keep every row, and add a flag that says what is wrong. Someone later can choose what to do with it. A deleted row cannot be explained later.

Lv 2 · How the check works

zone_flag takes the first rule that applies, in this order:

  1. 'unmatched': either id is NULL or not in zones;
  2. 'unknown': either id is 264;
  3. 'outside_nyc': either id is 265;
  4. 'ok'.

The order matters: test 'unmatched' first.

Lv 3 · The real SQL

CASE WHEN /* a pickup or drop-off with no match */ THEN 'unmatched'
     WHEN t.pu_location_id = 264 OR t.do_location_id = 264 THEN 'unknown'
     WHEN /* ... 265 ... */ THEN 'outside_nyc'
     ELSE 'ok' END AS zone_flag

Count before and after

7,171 rows in, 7,171 rows out. No row is lost, and each one carries a flag.

Lv 2 · How the check works

Flags: ok 6,962, unknown 110, outside_nyc 74, unmatched 25. Together they make 7,171.

The check passes when trips_clean has 7,171 rows, keeps every column of trips unchanged, and has the expected (row_id, pu_zone, do_zone, zone_flag) values.

Lv 3 · The real SQL

SELECT zone_flag, count(*) AS trips
FROM trips_clean
GROUP BY zone_flag
ORDER BY trips DESC;
