## What this is

A browser game for BADM 554 modeled on Armin Ronacher's Cube Crawler
(https://github.com/mitsuhiko/dungeon-crawler, guide at /learn/). The pattern to keep, in
Vishal's words: "an agent in chat is available to help modify the game at runtime and also
explains the code as needed during the game. The agent has visibility into the game as well."

Three parts make that pattern work (from the Cube Crawler `learn/README.md`):
1. The tutor sees the live state with every message (where the player is, what they did, the game window).
2. The tutor can change the running game, and every change can be undone (pause, step, slow,
   lenses that draw the rules, tune values with a reset).
3. Explanations go in levels: 1 big idea, 2 how it works, 3 the real code, read live from source.
   The tutor teaches by asking back, and it teaches ideas, not prompting.

## Open questions (must be settled before learners touch it)

Questions 1 and 2 were settled in the design session (above). Questions 3 and 4 are settled in
`docs/design-spec.md` (DuckDB-WASM in the browser; WCAG 2.1 AA, keyboard, 375px).


1. **Student data.** Vishal's rule: student data (including bot chat logs) goes only to Codex Edu.
   A student-facing tutor on the Anthropic API sends learner messages to Anthropic. Decide if
   that is allowed for this game, or if the tutor runs on Lumen (campus-hosted) for students and
   Anthropic only for staff testing. Reference: `~/admin/agent-infra/codex-accounts.md`.
2. **Cost and abuse guardrails.** The Anthropic key stays server-side, never in the browser.
   Per-student and per-session caps, input caps, max turns, and a hard spend cap on a separate
   Console workspace. The 2026-10-16 promo credit expires that night, so the pilot needs a
   paid, capped key.
3. **Data size.** A browser-sized taxi extract (DuckDB-WASM or SQLite-WASM) versus a server.
4. **Accessibility.** WCAG 2.1 AA, keyboard play, works at 375px.
